Scheduling Draft proposal v2

Adaptive Profile Handler v2

Status: Draft for discussion. One proposed plugin prepares request load and selects the profile. The adaptive plugin is not implemented.

Review basis: Local code at commit 8a2f37d3, inspected on 2026-09-29.

1. Foundations: plugin, profile, and handler

The handler selects a profile. The profile groups the plugins that filter, score, and pick a pod. The handler then returns the scheduling result. A small dot marks existing components. The scheduler invokes these steps; request parsing, admission, and data preparation are omitted.

YAML example: handler, profile, and plugins

This configuration uses existing plugin types. It assumes workers eligible for the decode filter, supported backend metrics, and pool/discovery configuration in the deployment. Omitted producers and data-layer components are supplied through the default-injection mechanism. This example has not been tested against a cluster as part of this document.

YAML
apiVersion: llm-d.ai/v1
kind: EndpointPickerConfig

plugins:
  # Handler plugin: chooses which profile runs.
  - type: single-profile-handler

  # Filter plugin: keeps eligible pods.
  - type: decode-filter

  # Three separate scorer plugins.
  - type: prefix-cache-scorer
  - type: kv-cache-utilization-scorer
  - type: queue-scorer

  # Picker plugin: selects from the combined scores.
  - type: max-score-picker

schedulingProfiles:
  - name: balanced
    # References five scheduling plugins; the handler is configured above.
    plugins:
      - pluginRef: decode-filter
      - pluginRef: prefix-cache-scorer
        weight: 2
      - pluginRef: kv-cache-utilization-scorer
        weight: 1
      - pluginRef: queue-scorer
        weight: 1
      - pluginRef: max-score-picker

This example explicitly configures six plugin instances: one handler, one filter, three scorers, and one picker. The balanced profile references the five scheduling plugins. The handler is configured separately and selects balanced because it is the only profile.

Responsibilities

ConceptResponsibilityExample
PluginImplements one or more extension points. A plugin can filter endpoints, score them, pick a result, prepare data, or handle profiles.queue-scorer computes a score from each candidate's waiting queue.
Scheduling profileA named configuration of filter, scorer, and picker plugins, with weights for scorers. It defines how to choose endpoints when that profile runs.balanced combines prefix reuse, KV utilization, and queue depth.
ProfileHandlerA plugin that chooses which profiles the scheduler runs and processes their results.single-profile-handler always runs the sole configured profile and marks it as primary.

Here, "handler" means ProfileHandler. The EPP also has request-handling components that parse and process traffic; those have separate responsibilities. A ProfileHandler is itself a plugin, configured under the top-level plugins list. It is not part of a profile's filter/scorer/picker list.

Real-world analogy: choosing a hotel

Consider a travel service choosing a hotel for each trip.

Router conceptTravel-service equivalentConcrete example
PluginA reusable tool that performs one task.A budget filter excludes expensive hotels; location and comfort scorers rate the remaining hotels; a picker selects the highest combined score.
ProfileA named selection policy that groups tools and sets their priorities.A business-trip profile gives location weight 4 and comfort weight 1. A family-trip profile uses the same tools with location weight 1 and comfort weight 4.
HandlerThe planner that chooses which selection policy to use.For a work trip, choose business-trip. For a family holiday, choose family-trip.

For a work trip, the handler selects the business-trip profile. Its filter removes hotels over budget, its scorers rate the eligible hotels, and its picker selects a hotel using the weighted scores. The budget remains a hard constraint; the weights express preferences among eligible hotels.

The same plugins can serve both profiles. Changing the selected profile changes how their results are combined. The planner's choice between trip policies illustrates the proposed adaptive handler; the existing single-profile-handler example always uses its sole configured profile.

Plugin roles inside a profile

RoleResponsibilityPlugin in the example
FilterRemoves ineligible candidates before scoring.decode-filter
ScorerAssigns each candidate a score between 0 and 1, where higher is preferred. The scheduler applies its configured weight.prefix-cache-scorer, kv-cache-utilization-scorer, queue-scorer
PickerChooses endpoints from the combined scores.max-score-picker
ScorerMeaning
prefix-cache-scorerMatches the request's prefix against an endpoint's cache
kv-cache-utilization-scorerFavors endpoints with lower KV-cache utilization
queue-scorerFavors endpoints with shorter waiting queues

A DataProducer is another plugin role: it prepares data before scheduling. It is relevant to the proposal's load signal, but it does not belong in a scheduling profile's plugin list.

Connecting the YAML to the runtime behavior

  • plugins creates the plugin instances. type identifies the implementation; an optional name identifies an instance. If name is omitted, it defaults to type.
  • schedulingProfiles defines the balanced profile. Each pluginRef points to an instance from plugins. Each weight belongs to that scorer reference within the profile.
  • single-profile-handler needs no profile-name parameter: it selects the sole configured profile. The example declares it explicitly, although the default-injection mechanism can supply it.
  • The profile runs its filters, scorers, and picker in their respective stages. Weights remain fixed while scores respond to request and endpoint data.

For an illustrative request, assume two eligible endpoints receive these normalized scores:

EndpointPrefix score, weight 2KV-utilization score, weight 1Queue score, weight 1Weighted total
A1.00.20.02.2
B0.00.81.01.8

The handler selects balanced; the scorers supply the values; the scheduler adds the weighted contributions; and max-score-picker selects A. These values illustrate the calculation and are not benchmark results.

Proposal overview

  • Users configure one adaptive-profile-handler instance, predefined profiles, and ordered selection rules. The EPP selects a profile per request without a profile-selection header.
  • The same instance implements DataProducer.Produce and ProfileHandler.Pick / ProcessResults. It reads existing data-layer metrics and keeps its summary and decision on the request.
  • The MVP supports mean waiting-queue depth over request candidates. The design uses existing extension points and plugin parameters, with no new CRD. Performance improvement remains a hypothesis to measure.

2. Problem and scope

Users may favor prefix reuse under low load, request distribution under high load, and a balanced policy between those conditions. Rules select among profiles with fixed scorer weights.

  • A homogeneous pool of workers capable of serving the complete request.
  • Profiles with the same endpoint eligibility requirements and inference stage; only scorer weights differ.
  • One configured adaptive plugin, one supported metric (waitingQueueSize), and one aggregation (mean).
  • Per-request selection with a mandatory default profile and fixed, ordered rules.

Configuration hot reload, automatic weight adjustment, arbitrary metric expressions, shared active-profile state, hysteresis, and composition of multiple profile handlers are outside the MVP. Concurrent requests can select different profiles.

3. Proposed flow

A small dot marks existing data or framework mechanisms; NEW marks proposed behavior. Produce, Pick, and ProcessResults belong to the same plugin instance. The request-control director and scheduler invoke them at their existing stages.

Other producers and admission retain their existing responsibilities. Each request owns its summary and decision; the shared plugin instance holds configuration.

4. Existing handler context

The existing header-profile-handler selects a configured profile using a request header, named EPP-Profile by default, with a configured default when the header is absent. A caller or upstream component supplies the choice. The proposed adaptive handler makes that choice inside the EPP using load signals and configured rules.

The existing disagg-profile-handler demonstrates internal decisions without a client profile header: it determines which inference stages to schedule. The proposed adaptive handler selects a scheduling policy for the same serving task. The loader allows only one ProfileHandler, so combining adaptive selection with disaggregation requires separate design and is outside this proposal's scope.

5. Why not use one combined profile?

A combined profile is a useful baseline and is already supported. A repository configuration combines prefix-cache matching, KV-cache utilization, and waiting-queue depth.

The scheduler adds weighted scores. A combined profile responds to changing signals, but its weights do not change automatically. Including every plugin does not guarantee improvement: filters can reduce the candidate set, signals can overlap, and each profile allows one picker.

The queue scorer normalizes scores relative to candidates with recorded metrics. It skips endpoints whose metrics have never been updated; when all recorded queue depths are equal, each scored endpoint receives 1. Queue depths of 0, 10 and 100, 110 produce the same relative scores. An absolute load signal could trigger a different policy, although mean queue depth is not a model of capacity or waiting time.

6. Proposed selection contract

All adaptive plugin parameters below are proposed. The MVP accepts only the listed metric and aggregation.

FieldProposed meaning
defaultProfileRequired profile when no rule matches or the summary is unavailable
maxMetricAgePositive duration limiting the age of every candidate metric; 1s in the example
rulesOrdered list; the first match wins
rules[].nameUnique rule identifier for diagnostics
rules[].when.metricwaitingQueueSize, mapped to the existing Metrics.WaitingQueueSize field
rules[].when.aggregationmean, computed over the candidate population defined in section 7
rules[].when.operatorgte or lt
rules[].when.valueFinite, non-negative threshold in queued requests per candidate
rules[].profileProfile name defined in schedulingProfiles
  • Validate profile references, rule names, metric, aggregation, operator, thresholds, and duration at startup. Unknown fields are errors.
  • At the first Pick, read the summary once. Use the first matching rule, or defaultProfile when no rule matches or the summary is absent or invalid. Store the choice on the request.
  • Keep that choice for the request. A late summary cannot change it. After the selected profile has run, subsequent Pick calls return no profiles.
  • ProcessResults requires exactly one result for the stored choice and sets PrimaryProfileName to that profile. A missing, nil, or unexpected result is a scheduling error. There is no retry through an alternative profile.
  • The default profile remains subject to admission, endpoint availability, and its filters.

Record the selected profile, matched rule or default reason, and summary validity once per request. Count selections and fallbacks with configured profile and rule names and a fixed set of reason labels. Report an absent summary as absent; absence alone does not reveal whether Produce failed, timed out, or was skipped.

7. Reusing the data layer

The data layer already stores endpoint metrics, and the pool metrics logger already computes averages. The adaptive plugin reuses the endpoint snapshots and the arithmetic meaning of a mean. Its calculation is scoped to the request candidates.

Existing data or calculationScopeUse in this proposal
WaitingQueueSize and UpdateTimeEach endpoint snapshotInputs read directly by Produce
Mean queue, KV-cache utilization, and running requestsPool pods with fresh metrics; periodically exported to PrometheusRelated calculations; the local handler has no direct summary accessor
Multicluster queue and KV-cache attributesAggregate metrics scraped from a remote pool onto a cluster endpointAvailable for multicluster routing; outside the local-pod MVP
Utilization saturation detectorMean of each endpoint's maximum normalized queue or KV utilizationRelated policy with different units and stale-data behavior

A pool with queues 0, 0, 30 has mean 10. If screening leaves only the first two pods for a request, its candidate mean is 0. Pool-wide averages can therefore select a different policy. The existing logger also excludes stale pods and rounds its averages; the MVP uses the unrounded candidate mean and the full-coverage rule below.

Candidate summary

  • Produce receives candidate snapshots after discovery and screening, before profile filters.
  • Compute the arithmetic mean of WaitingQueueSize once for this request. The value is valid only when the population is nonempty and every candidate has recorded, fresh metrics.
  • Missing metrics, timestamps older than maxMetricAge, future timestamps, and negative queue values make the summary unavailable. Missing data must not be treated as queue depth zero.
  • Retain candidate count, metric update times, and validity reason in the immutable summary. Pick rechecks freshness at selection time so a delayed request cannot use an expired summary.
  • Use existing snapshots in memory. The plugin performs no metric scraping or network calls during Produce or Pick.

All profile alternatives must have the same eligibility requirements, and summarized candidates must satisfy those requirements. Different eligibility groups require a separate population contract. Full coverage can cause fallback during pod startup; partial coverage is outside the MVP.

One instance, two extension points

The loader discovers ProfileHandler implementations, while request control independently discovers DataProducer implementations. The proposed instance implements both interfaces. Produce prepares its request-local summary before the scheduler calls Pick, using the existing attribute store.

Declare WaitingQueueSizeKey from the core metrics extractor as a required data dependency, following queue-scorer. ScopedEndpoint.GetMetrics() exposes UpdateTime for freshness checks. Declare the typed summary in Produces() and its consumption in Consumes(), with the same instance-scoped DataKey. The dependency graph skips edges from a plugin to itself; execution-stage order supplies the Produce-before-Pick ordering. Namespace summary and decision keys by the configured instance name.

The director logs producer errors and continues request processing. A failure stops later producers, so the adaptive Produce hook can be skipped. The default producer timeout is 400 ms and can be overridden by a timeout-aware producer. Cancellation does not wait for the producer goroutine to stop or roll back request attributes.

Produce computes the summary locally, checks cancellation before publication, and writes one complete immutable value. Pick accepts the complete, valid value visible at its first call; otherwise it selects the default. A published value alone does not prove that the executor reported success. The stored decision prevents later writes from changing the selected profile.

8. Complete proposed YAML example

This configuration cannot run on the existing implementation. adaptive-profile-handler and all its parameters are proposed. The plugin implements both preparation and selection. The existing loader rejects unregistered plugin types.

The example configures one adaptive instance and three profiles. The existing metrics infrastructure is supplied through the default-injection mechanism. The proposed selector waitingQueueSize maps to WaitingQueueSize; aggregation: mean describes the calculation performed by the plugin. Weights, thresholds, and maxMetricAge are illustrative. Pool and deployment assumptions match the foundations example.

YAML
apiVersion: llm-d.ai/v1
kind: EndpointPickerConfig
plugins:
  - type: adaptive-profile-handler
    name: adaptive
    parameters:
      defaultProfile: balanced
      maxMetricAge: 1s
      rules:
        - name: high-queue
          when:
            metric: waitingQueueSize
            aggregation: mean
            operator: gte
            value: 20
          profile: load-oriented
        - name: low-queue
          when:
            metric: waitingQueueSize
            aggregation: mean
            operator: lt
            value: 5
          profile: cache-oriented
  - type: decode-filter
  - type: prefix-cache-scorer
  - type: kv-cache-utilization-scorer
  - type: queue-scorer
  - type: max-score-picker
schedulingProfiles:
  - name: balanced
    plugins:
      - pluginRef: decode-filter
      - pluginRef: prefix-cache-scorer
        weight: 2
      - pluginRef: kv-cache-utilization-scorer
        weight: 1
      - pluginRef: queue-scorer
        weight: 1
      - pluginRef: max-score-picker
  - name: cache-oriented
    plugins:
      - pluginRef: decode-filter
      - pluginRef: prefix-cache-scorer
        weight: 4
      - pluginRef: kv-cache-utilization-scorer
        weight: 1
      - pluginRef: queue-scorer
        weight: 1
      - pluginRef: max-score-picker
  - name: load-oriented
    plugins:
      - pluginRef: decode-filter
      - pluginRef: prefix-cache-scorer
        weight: 1
      - pluginRef: kv-cache-utilization-scorer
        weight: 1
      - pluginRef: queue-scorer
        weight: 4
      - pluginRef: max-score-picker

All profiles reference the same scorer instances. A weight belongs to the reference within a profile; the loader creates a weighted scorer for each reference. The same pluginRef can therefore have different weights in different profiles.

The 0, 0, 30 scenario illustrates a limitation of the mean. Choosing a percentile, maximum load, or predicted waiting time is a separate policy decision with different semantics.

Stateless selection has no hysteresis: metric fluctuations around 5 or 20 can switch the chosen profile between consecutive requests. The balanced interval provides a default region between the two thresholds. Holding a profile across requests would require an explicit state scope and transition policy outside the first version.

EPP configuration deliveryFile through --config-file, or text through --config-text

In the inspected path, EndpointPickerConfig is process configuration. Its apiVersion and kind fields do not require creating a Kubernetes custom resource. PluginSpec.Parameters contains raw JSON decoded by the plugin factory. The proposed schema can therefore live in plugin parameters without adding a CRD. Implementation requires one plugin type implementing DataProducer and ProfileHandler, runner registration, dependency declarations, and parameter validation. The design uses existing hook signatures and the request attribute store.

Example ConfigMap wrapper containing a baseline made from existing components:

YAML
apiVersion: v1
kind: ConfigMap
metadata:
  name: epp-config
data:
  epp-config.yaml: |
    apiVersion: llm-d.ai/v1
    kind: EndpointPickerConfig
    plugins:
      - type: single-profile-handler
      - type: decode-filter
      - type: queue-scorer
      - type: max-score-picker
    schedulingProfiles:
      - name: balanced
        plugins:
          - pluginRef: decode-filter
          - pluginRef: queue-scorer
            weight: 1
          - pluginRef: max-score-picker

The ConfigMap must be in the EPP's namespace. In the inspected deployment, it is mounted at /etc/epp, and the EPP reads /etc/epp/epp-config.yaml. Once the proposal is implemented, the key can contain the adaptive configuration. This wrapper distributes configuration; it is not a complete Deployment.

Configuration is read at startup and retained in memory. Selection among loaded profiles requires no restart. Changing rules, weights, or the plugin list requires a restart in the existing path. Updating a ConfigMap alone does not guarantee reload or restart. Hot reload is a separate extension.

10. Alternatives and tradeoffs

AlternativeBenefitCost or limitation
Fixed combined profileSupported, small configuration, measurable baselineWeights do not change with operating conditions
Header-based profile selectionExisting header-profile-handler selects among configured profilesA caller or upstream component must supply the choice; the handler does not evaluate load rules
Rule-based profile selectionExplicit rules and profiles users understandThreshold tuning, profile maintenance, and sensitivity to metrics
Scorer with a continuous policyCan account for costs per request and endpointRequires a scoring model, calibration, and explainable results

This draft recommends rule-based profile selection because it matches the requirement for user-controlled, predefined alternatives. If improvement requires continuous decisions for each endpoint, a custom scorer should also be evaluated.

11. Decisions before implementation

  • Choose a serving workload and profile alternatives with shared endpoint eligibility.
  • Choose the workload metric used to measure improvement, then calibrate queue thresholds and scorer weights.
  • Confirm the candidate population, full-coverage policy, and maxMetricAge for the deployment.

If you do one thing: choose a workload where a fixed profile performs inadequately and measure whether mean-queue rules improve its results. Nontrivial implementation work requires a linked issue under the project contribution rules.

Verification status

This draft is based on inspection of the existing data layer, pool-average calculations, extension-point registration, dependency graph, and request attribute store. Document checks cover the three YAML examples, nested ConfigMap configuration, profile references, and illustrated rule selections.

The adaptive plugin and its schema are proposed and have not been executed in the EPP. Valid YAML syntax and existing interface support do not establish runtime correctness or performance benefit.
