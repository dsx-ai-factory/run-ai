Today · adaptive routing, in progress

Background detectors retune the weights

✅ Endpoint metrics store  ──►  🆕 Imbalance detector   CVn of KV usage and assigned requests, pool-wide
                           ──►  🆕 Pressure detector    Σ waiting / Σ (waiting + running)
                                        │  smoothed 0.1 × prev + 0.9 × new
                                        ▼
                                 🆕 Adaptive configurator  sigmoid(imbalance) → distribution budget D, affinity A = 1 − D
                                        │  rewrites scorer weights inside every profile, each cycle
                                        ▼
                                 ✅ Scheduler              requests use the current weights; zero per-request work
  • Merged prerequisites: #2119 scorer categories (affinity / distribution), #2207 float weights.
  • Experimental branch adaptive-with-pressure; hotspot benchmark reported on 8 × A100.
  • Output is a continuous, derived weight vector. #1992 also lists an alternative: select among groups of scorers instead of adjusting each weight.

The proposal · step 6 of 14 · 🆕 new step

Our profile handler adaptive-profile-handler: Produce

Our profile handler, a new ProfileHandler plugin type named adaptive-profile-handler (one instance per EPP, takes the single handler seat instead of single-profile-handler; the same instance also implements DataProducer, which is why it runs here), walks the same three pods once and writes two numbers on the request: how uneven the queues are (cv = σ / mean, capped at 1, 0 when the mean is below a small gate) and how much is waiting overall (P = waiting / (waiting + running)). If any pod's numbers are missing or older than maxMetricAge, it marks the summary invalid instead. No decision yet.

The proposal · step 8 of 14 · 🆕 new step

Our profile handler adaptive-profile-handler: Pick

The scheduler asks for a profile. Our profile handler (its Pick hook) first asks: "which profile did I choose last time, and is the signal still inside that profile's stay band (above its exit threshold)?" If yes, keep it. If no, take the first rule whose enter threshold holds: very uneven → load-oriented, almost nothing waiting → cache-oriented; otherwise the default. It stores the choice in a field on the profile handler instance (in the EPP process, guarded by a mutex), so the next request's Pick starts from it. A restart resets it.

The proposal · why these three steps

What the three steps buy you

1 · Stable, not twitchy

cv  0 ────────┼──────────────┼────────► 1
           exit 0.35      enter 0.5
  balanced  │  stay as you are  │  load-oriented

same noise  0.48 0.52 0.47 0.55 0.40 0.30
without memory   4 flips in 6 requests
with memory      1 in, 1 out

Sticky to the profile until the signal leaves its band. Sticky to the pod only as long as the profile lets the prefix win.

2 · Explainable

One log line and one counter per request: rule=hotspot entered cv=1.00 → load-oriented → pod-1. Not a derived weight vector.

3 · Operator-controlled

Humans write the three profiles; the system only chooses among them. Bounded by construction.

4 · Portable

Thresholds are ratios in 0..1. One YAML for an 8B model on one GPU and a 70B on eight.

5 · Cheap

Same metrics, one extra pass per request, no new CRD, no new scraping.

Number 1 is the one the background configurator does not have: it smooths the signal but has no memory of the decision.

Proposal · configuration

What the operator writes

- type: adaptive-profile-handler
  parameters:
    defaultProfile: balanced
    maxMetricAge: 1s
    minMeanQueue: 3        # gate for cv
    smoothing: 0.1         # α, 0 disables
    rules:
    - name: hotspot
      when: { signal: imbalance, operator: gte,
              enter: 0.5, exit: 0.35 }
      profile: load-oriented
    - name: idle
      when: { signal: pressure, operator: lt,
              enter: 0.2, exit: 0.3 }
      profile: cache-oriented

Key point · thresholds are ratios, not counts

Pool20 waiting is…P
8B · 1 × A100 (~256 slots)~8%, idle0.07
70B · 8 × A100 (~32 slots)~60%, busy0.38

"20 waiting requests" means nothing without capacity. P and cv carry the capacity inside the ratio, so one YAML works on every model and GPU. The only count left is the gate "is there anything worth redistributing".

Profiles unchanged: cache 4/1/1 · balanced 2/1/1 · load 1/1/4. The only new plugin type is adaptive-profile-handler; it takes the single ProfileHandler seat that single-profile-handler fills by default today. Startup validation: exit < enter for gte, exit > enter for lt.
