InfW → WorkloadRunner
Inference Migration

Sunsetting the legacy InferenceWorkload CRD onto a generic WorkloadRunner + plugins path

Part 1 of 2 · Single-replica only

ⓘ Status surface — revision names, external URLs, phase mapping, PluginStatus — is tracked separately and covered later.

TL;DR

Three things to remember

Composer is the heavy lift. The cluster-side controller knows nothing about inference — it follows the Karta for the target kind, applies plugins, and reconciles.
  • Most fields map cleanly — InferenceFields become Knative annotations; Knative handles the runtime behaviour natively.
  • The serving-port pattern doesn't change — port-bearing OAuth2-proxy sidecar composed into the Knative template by the CP composer (Liran's design — in review). No new corev1.Service for InfW.
  • Tools (exposedUrls) need multi-endpoint — one OAuth2-proxy sidecar per URL. Blocking dependency on PR #19525.

⚠ Schema-version note: every YAML in this deck uses the target WLR schema — instructions.networking.endpoints[] (post-PR #19525) for Service + Ingress. The OAuth2-proxy sidecar for auth is composed at the CP composer level (Liran's design — in review) directly into the Knative pod template's containers[]. There is no instructions.initContainer.* field on WorkloadRunner — sidecar/init-container composition is a CP feature, not a runtime plugin. Nothing migrates until PR #19525 + Liran's CP composer design land.

What the composer emits

The WorkloadRunner CR

apiVersion: run.ai/v1alpha1
kind: WorkloadRunner
metadata: { name: my-llm, namespace: runai-team-a }
spec:
  template:
    apiVersion: serving.knative.dev/v1
    kind: Service
    spec:
      template:
        metadata:
          annotations:
            autoscaling.knative.dev/metric: rps
            autoscaling.knative.dev/target: "100"
            autoscaling.knative.dev/min-scale: "0"
        spec:
          containers:
          # CP composer bakes OAuth2-proxy sidecar HERE when auth is on:
          - name: oauth2-proxy                          # port-bearing 4180 → Knative routes here
            ports: [{ containerPort: 4180 }]
          - name: model
            image: my-llm:latest
            ports: [{ containerPort: 8080 }]            # user container — NOT port-bearing
          containerConcurrency: 0      # concurrencyHardLimit
          timeoutSeconds: 300          # requestTimeoutSeconds
  instructions:
    networking:                                            # network plugin: Service + Ingress only
      endpoints:
      - services: [{ ref: { name: my-llm, port: 80 } }]    # Knative auto-Service (→ 4180)
        externalAccess: { ingress: { ... } }

Worked examples · part 1

From the field-mapping table

General · createHomeDir

# API request body
{
  "createHomeDir": true,
  "security": { "runAsUid": 1001 }
}

# WLR
containers:
- env: [{ name: HOME, value: /home/runai-1001 }]
  volumeMounts: [{ name: home, mountPath: /home/runai-1001 }]
volumes: [{ name: home, emptyDir: {} }]

One flag → 3 correlated pod-spec edits: volume + mount + HOME env.

Compute · gpuPortionRequest (fractional)

# API request body
{
  "compute": { "gpuPortionRequest": 0.5 }
}

# WLR
spec.template:
  metadata.annotations:
    gpu-fraction: '0.5'     # Run:ai-specific
  spec.containers:
  - name: model
    # NO nvidia.com/gpu — fractioner binds the device

Fractional GPU is a Run:ai annotation, not a k8s resource limit.

Scheduling · nodePools[]

# API request body
{
  "nodePools": ["gpu-pool-a", "gpu-pool-b"]
}

# WLR
pod.spec.affinity.nodeAffinity:
  preferredDuringScheduling...:      # ordered preference
  - { weight: 2, key: run.ai/nodepool, values: [gpu-pool-a] }
  - { weight: 1, key: run.ai/nodepool, values: [gpu-pool-b] }

Preferred, not required — input order = priority via decreasing weight.

Worked examples · part 2

From the field-mapping table

servingPort · port + auth

# API request body
{
  "servingPort": {
    "container": 8080,
    "authorizationType": "authorizedUsersOrGroups",
    "authorizedUsers": ["alice@x.com"]
  }
}

# WLR
spec.template.spec.template.spec.containers:            # CP composer bakes sidecar here
- name: oauth2-proxy, ports: [{ containerPort: 4180 }]    # port-bearing
- name: model, ports: [{ containerPort: 8080 }]
instructions.networking.endpoints:                       # network plugin only
- services: [{ ref: { name: my-llm, port: 80 } }]

Composed-in sidecar becomes port-bearing — no new corev1.Service. Networking plugin is unaware of the sidecar.

autoscaling · annotations + 1 spec field

# API request body
{
  "autoscaling": {
    "metric": "throughput",
    "metricThreshold": 100,
    "concurrencyHardLimit": 32
  }
}

# WLR
spec.template:
  metadata.annotations:
    autoscaling.knative.dev/metric: rps    # enum rename
    autoscaling.knative.dev/target: '100'
  spec.containerConcurrency: 32           # direct field

11/12 fields → stringified annotations. concurrencyHardLimit is the lone first-class spec field.

Auth · vocab mapping

# API request body
{
  "servingPort": {
    "container": 8080,
    "authorizationType": "authorizedUsersOrGroups",
    "authorizedUsers": ["alice@x.com", "bob@x.com"]
  }
}

# WLR — chosen by which list is populated
endpoints[0].auth:
  authorizationType: authorizedUsers     # users-list set
  authorizedUsers: [alice@x.com, bob@x.com]

When source is authorizedUsersOrGroups, the WLR target is chosen by which list is set.

Label trigger · NIM

# API request body
{
  "labels": [
    { "name": "runai.nim/workload", "value": "true" }
  ]
}

# WLR — TWO effects from the one label
spec.template.spec.template.metadata.labels:
  runai.nim/workload: 'true'              # propagated to pod
instructions.networking.endpoints:
- name: metrics                           # extra endpoint
  services: [{ create: { ports: [{ port: 8000 }] } }]

Label triggers two things: pod-label propagation + extra metrics endpoint (no auth, no Ingress).

  • Trigger: runai.nim/workload=true label — not a spec field.
  • Why a label? NIM is a pure overlay on top of InfW — metrics on an unauthenticated port, NIM-specific service labels for Prometheus discovery, label propagated to the pod for ServiceMonitor matching. Keeping it label-driven lets the InfW spec stay stable while NIM behaviour is opted-in.
  • How NIM metrics work: NIM containers expose Prometheus metrics on :8000. Composer emits a dedicated ClusterIP <workload>-metrics Service carrying runai.nim/workload=true + runai.nim/workload-metrics-service=true labels. A cluster-wide ServiceMonitor selects those labels and scrapes the pods directly — bypassing the OAuth2-proxy on the serving path. No auth, no Ingress. (Legacy: BuildNIMMetricsService at utils.go:562-617.)
spec:
  template:
    spec.template.metadata.labels:
      runai.nim/workload: 'true'     # propagated from WLR labels

    - name: oauth2-proxy                          # port-bearing 4180 for serving
    - name: model

  • Knative pod-template allows exactly one containerPort. That slot is reserved for the servingPort. Every ports[] entry must therefore route through the networking plugin only — NOT declared on containers[0].ports[].
  • Composer behaviour: one networking endpoint per ports[] entry, with services[].create using the requested serviceType (ClusterIP / NodePort / LoadBalancer). The plugin's Service selects the Knative pod by its standard runai/workload label.
  • Behavior change from legacy: legacy InfW silently drops non-serving ports (utils.go:528-536). The new path honors them — that's what the user asked for by setting serviceType.

Dependencies & Deliverables

What we ship · what we depend on

One plugin + one CP composer feature

Networking plugin + sidecar composition (CP)

The composer drives the runtime networking plugin and bakes the OAuth2-proxy sidecar directly into the template's pod spec. There is no InPod mode in the networking plugin; there is no instructions.initContainer.* field on WorkloadRunner. Sidecar/init-container composition is a CP responsibility, not a runtime plugin.

Networking plugin · runtime · what it does

  • Creates corev1.Service (or refs the Knative auto-Service)
  • Creates Ingress / Route / HTTPRoute
  • Does not inject sidecars or know about auth
  • Blocker: PR #19525 for multi-endpoint (maxItems > 1) needed for tools

CP composer feature · Liran's design · what it does

  • Bakes the OAuth2-proxy sidecar directly into the Knative pod template's containers[] (port-bearing → Knative auto-Service routes through it)
  • Same feature also bakes git-sync + S3 as init-containers into the template
  • No new field on WorkloadRunner — sidecar appears in the template's pod spec
  • Blocker: Liran's CP composer design — in review
Decision: hard-block on both. Networking plugin's Standalone mode (separate Deployment) is not a fallback for inference — it'd regress every existing InfW (Knative's auto-Service would still target the unprotected user container).

What we ship

Deliverables for InfW migration

  1. CP composer — every InfW field → WLR template or instructions. Translation rules per infw-fields.html. Also owns anything the Karta doesn't surface — writes straight into spec.template.
  2. Knative-Service Karta — already ships (BuildKNativeServiceV1). No work here.
  3. Networking-plugin v2 — multi-endpoint per PR #19525 (Service + Ingress; no sidecar / no InPod here).
  4. CP composer feature (Liran) — composer bakes OAuth2-proxy sidecar (+ git-sync, S3 init-containers) directly into the template's pod spec. Not a runtime plugin.
  5. Composer networking behaviour — emit one endpoint per exposedUrls[] entry; services[].ref at Knative auto-Service for serving; emit metrics endpoint when NIM label is present.
  6. Validation — reject ambiguous authorizedUsersOrGroups (both users-list and groups-list set).
