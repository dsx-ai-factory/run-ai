01 · Architecture and request flow · before / after

Before: a Service picks a leader at random. After: EPP picks it, the Gateway delivers.

Before · LWS serving as Run:ai composes it today

Two routing decisions today, both blind: the Ingress picks the Service by host, the Service picks a leader at random.

🆕 NEW rendered by the InferenceEndpoint controller today · 🔜 PLANNED proposed, not built · green request path · orange cold / fallback path · blue dotted internal · dashed grey = config / metrics
1. Client sends the request to the Run:ai URL; the Ingress terminates TLS.
2. Ingress forwards to the leader Service port.
3. kube-proxy picks ANY leader endpoint, round-robin / random.           ⚠ ignores queue depth and KV cache
4. Leader (oauth2-proxy if protected → vLLM) runs the request across its workers.
5. Response streams back the same way.                                   ✓

After · same workload, InferenceEndpoint stack beside it

Gateway + EPP replace Ingress + Service for the new hostname. The old pair is not deleted; it keeps serving the old URL until DNS moves. Nothing under the leader changes.

🆕 NEW rendered by the InferenceEndpoint controller today · 🔜 PLANNED proposed, not built · green request path · orange cold / fallback path · blue dotted internal · dashed grey = config / metrics
1. Client sends the request to the hostname in routing.hostnames; the Gateway terminates TLS.
2. Gateway asks EPP over gRPC (ext_proc): "which leader for this request?"
3. EPP scores the ready leaders (queue · KV cache · prefix) and returns one IP:port.    ✓ smart pick
4. Gateway forwards the request straight to that Pod. The Service is not on this path.
5. Leader (oauth2-proxy if protected → vLLM) runs the request across its workers.      ✓ identical to before
6. Response streams Pod → Gateway → client. EPP is not in the stream.                   ✓

Detailed sequence · one request on the new path

EPP is consulted once per request and only returns an address. The Gateway carries the bytes. Workers never see the Gateway.

🆕 NEW rendered by the InferenceEndpoint controller today · 🔜 PLANNED proposed, not built · green request path · orange cold / fallback path · blue dotted internal · dashed grey = config / metrics
0. In the background, EPP scrapes /metrics on every ready leader: queue depth, KV cache use, prefix index.
1. Client sends POST /v1/chat/completions to model.example.com with its bearer token.
2. Gateway matches the HTTPRoute, sees backend = InferencePool, asks EPP over ext_proc.
3. EPP drops unready leaders, scores the rest (queue 30, KV 20, prefix 10), picks the group 1 leader.
4. EPP answers with that leader's Pod IP and port, optionally rewriting the model name.
5. Gateway forwards the original request to that IP:port.                                  ✓ workers never involved
6. On the leader, oauth2-proxy checks the token (if protected), then hands to vLLM.        ✓ only if port = 4180
7. vLLM runs the request across its workers over NCCL / Ray; many forward passes.
8. Tokens stream back through the Gateway as SSE; the 300 s route timeout is the budget.  ⚠ long generations need more
9. Client receives the stream. Group 0 kept serving other requests the whole time.          ✓

🧠 Before, the doorman points at a random table. After, a maître d' with a headset picks the best table. The kitchen (LWS) never knew either of them existed.

03 · Lifecycle flows

What happens when the groups change

Scale up: replicas 2 → 3

1. User raises replicas; LWS creates group 2: one leader + workers.
2. Leader starts; TCP socket opens early.           ⚠ not serving yet
3. Workers join; shards load; leader readiness probe passes.
4. EPP sees a new ready Pod matching the selector.   ✓ automatic
5. Next scrape fills its metrics; it starts winning requests.

Group failure: a worker in group 0 dies

1. Worker Pod exits; NCCL collective in the leader fails.
2. Ask: does the leader go unready?
   → yes: EPP drops it on the next refresh.           ✓ traffic moves to group 1
   → no (TCP probe only): EPP keeps picking it.       ✗ errors until LWS restarts the group
3. LWS restarts the whole group (RecreateGroupOnPodRestart).
4. Leader ready again → back in the pool.            ✓

Rolling update: new image

1. LWS replaces groups one at a time.
2. Old leader gets SIGTERM; in-flight streams continue during grace.
3. Old leader fails readiness → EPP stops picking it. ✓
4. New leader ready → EPP adds it.                    ✓
5. Ask: is terminationGracePeriodSeconds ≥ longest stream?
   → no: streams cut mid-generation.                  ✗ set it

Replicas → 0

1. All groups deleted; pool is empty.
2. Request arrives; EPP has no candidates.
3. Gateway returns 5xx.                               ✗ no activator for LWS
4. Endpoint Ready stays True (route + EPP are fine). ⚠ misleading
→ Add a BackendsAvailable condition. Scale-to-zero was never an LWS feature.
04 · Risks and what to change

Different risks than Knative, all small

ConcernWhy it bites LWSWhat to change, whereSize
Readiness liesThe composer adds a TCP probe if none is set. The leader's socket opens long before all workers loaded their shards.Composer composer_v2/dinf_to_lws/: default to an HTTP readiness probe on the leader. Optional EPP filter: drop leaders with missing or stale metrics.S
Auth portProtected serving puts oauth2-proxy (4180) beside the leader. If workload.port is the model port, the new route bypasses auth.Controller inferenceendpoint_controller.go: when the Pod is protected, require workload.port = 4180, else Ready=False.S
Metrics portEPP scrapes /metrics on the routed port. Behind oauth2-proxy that is denied.Expose the vLLM metrics port separately; set it in the EPP metrics-data-source plugin in epp.yaml.S
Rolling update drainStreams cut when LWS deletes the old group.Composer: terminationGracePeriodSeconds ≥ longest expected stream; align with route timeout.S
Scorer compatibilityqueue / KV / prefix scorers expect vLLM metric names. TRT-LLM and SGLang differ.Per-engine validation; weight 0 for unsupported scorers.S
Replicas = 0No activator; pool empty → 5xx while Ready=True.Add BackendsAvailable condition (types + controller).S
Route path / timeoutOnly /v1 and 300 s are rendered.Expose routing.pathPrefixes and routing.requestTimeout (route.yaml, types).S
