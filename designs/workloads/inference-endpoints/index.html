The new InferenceEndpoint CRD,
next to the three inference types we already have

What we talk about today (3 lines)
  1. Run:ai has three inference workload types: DistributedInference (LeaderWorkerSet), Inference (Knative), NIMService (NIM operator). Each already composes its own CRD and routing.
  2. The new InferenceEndpoint CRD does not replace any of them. It is created in addition, from the same API request, and only changes the last hop: which Pod gets the request, chosen by an Endpoint Picker (EPP) instead of a random Service pick.
  3. Per type the fit is different: LWS is natural, NIM needs the auth proxy re-wired, Knative needs either an upstream change or a stack without Knative.
🔧 If you only remember one thing: one API call, two CRDs. The old one keeps owning the workload; the new one only owns the route to it.

Five spec branches, one per question: which Pods, which door, which picker, which model name, and (planned) which priority lane. Status answers "is the routing stack up", not "is the model up".

👤 user → Run:ai = user intent resolved by Run:ai · 🛠 admin = cluster policy · 🔜 = proposed, not in v1alpha1

Cross-field rules (CEL on the CRD)

RuleMeaning
epp.profile or epp.image requiredYou cannot have an empty epp.
image without profile → must be the approved GIE v1.5.0 imageNo arbitrary picker images.
profile + image → image must equal the profile's pinned imageNo version drift between profile and image.
scheduling.profiles ↔ profile: llm-d-v0.10Profiles only in llm-d mode, and llm-d requires profiles.
scorers and profiles cannot both be setOne scheduling model at a time.
defaultProfile / activeProfile must exist in profilesNo dangling names.
at least one scorer weight > 0A profile cannot ignore every signal.
🔜 objectives[].model unique; priority ≥ 0Planned with the objectives field. One lane per model name.

What the controller renders from it (owned children, same namespace)

InferenceEndpoint <name>
├── 🆕 HTTPRoute        <name>-route     parentRef = routing.gatewayRef · hostnames · PathPrefix /v1 · 300 s
│                                        backendRef → InferencePool
├── 🆕 InferencePool    <name>-pool      selector = workload.selector · targetPort = workload.port
│                                        endpointPickerRef → <name>-epp :9002 · FailOpen (FailClose with profiles)
├── 🆕 EPP Deployment   <name>-epp       image = epp.image or the profile's pinned image · Recreate on config change
│   ├── Service · ServiceAccount · Role · RoleBinding
│   └── ConfigMap                        scorers / profiles rendered into the GIE plugin config
├── 🆕 InferenceModelRewrite (optional)  one per spec.rewrites · deleted when rewrites is empty
└── 🔜 InferenceObjective (optional)     one per spec.objectives · priority per model name · EPP already has RBAC to read it

Everything the user sees in kubectl get after creating one endpoint. All children carry an ownerReference to it.

🔧 If you only do one thing: notice that workload.port is the only field that carries security meaning. Everything else is routing plumbing.
Pick a type

Each page has the same tabs: API → CRD · Architecture & flow · Lifecycle or Keeps/loses · Risks

LWS · DistributedInference

LeaderWorkerSet, one leader + workers per replica group
✅ The easy case
  • No router of its own; EPP is the only router
  • Pool = leaders only, via two labels Run:ai already uses
  • Risks: readiness probe, auth port 4180, metrics port
Open LWS →

Knative · Inference

Knative Service, revisions, Activator, scale to zero
⚠️ Needs a decision
  • Knative already owns routing and wake-up; GIE wants the same seat
  • Options: Gateway-failover hack, upstream Knative change, or KServe without Knative
  • Starts with "why not as-is", then the options
Open Knative →

NIMService · NIM operator

Operator-owned Deployment, Service, auth-proxy Deployment
⚠️ Easy routing, one auth gap
  • Pool = operator's frontend Pods, HTTP target port
  • The oauth2-proxy is a separate Deployment and gets bypassed
  • Fix: Gateway asks that same proxy via ext_authz
Open NIMService →

Glossary: GIE = Gateway API Inference Extension (InferencePool, EPP, InferenceObjective). EPP = Endpoint Picker, the component the Gateway asks "which Pod?". ext_authz = the Gateway asking an external service "allow or deny?" without routing bytes through it.
