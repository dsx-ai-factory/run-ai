01 · Why EPP cannot simply be bolted onto Knative

Knative already owns routing, activation and revisions. GIE wants the same seat.

Same two Pods, same load, on both sides. Left: Knative picks blindly but handles zero through the Activator. Right: GIE (Gateway API Inference Extension) picks from live load but has nothing to answer when the pool is empty. The red box is the hole Option A plugs with a Gateway backend failover to the Activator.

The four structural conflicts

#ConflictWhy it blocks a plain InferenceEndpointWhat would fix it
1Route ownershipKnative reconciles its own Ingress / HTTPRoute from the Route object and overwrites foreign edits. We cannot point its backend at an InferencePool.Knative learns the InferencePool backend kind (upstream change), or we add a second route on a second hostname.
2Scale to zeroA pool is a Pod selector. At zero it is empty and EPP has nothing to return; nothing calls the Activator.Gateway backend failover to the Activator (our hack, upstream EPP untouched), or Knative keeps routing at zero (upstream).
3RevisionsKnative splits traffic by revision percentage, tags and gradual rollout. A pool has no notion of a revision.One pool per revision with mirrored weights (fragile), or Knative emits per-revision pools (upstream).
4Accounting and auth in queue-proxyKPA scales on concurrency reported by queue-proxy; the oauth2-proxy sits behind it. Routing to the model port bypasses both.Pool target port = 8012, always. Solvable on our side.

Conflict 4 is ours to solve. Conflicts 1 to 3 are Knative's design, and every way around them is either an upstream change or a re-implementation of Knative behaviour outside Knative.

🔧 If you only do one thing: accept the premise before choosing an option: with Knative in the picture, EPP needs either a change in Knative or a second front door that re-implements part of Knative. The options tab is about which price to pay, or whether to avoid Knative for EPP-routed workloads altogether.

KServe in one paragraph

KServe is the CNCF model-serving layer that sits above the runtime. Its InferenceService CRD has a deployment mode switch: Serverless uses Knative underneath (revisions, Activator, scale to zero), RawDeployment uses a plain Kubernetes Deployment + Service + HPA with no Knative at all. Newer KServe versions add LLMInferenceService, an LLM-specific CRD that wires Gateway API and the GIE scheduler (InferencePool + EPP) natively, including prefill/decode and multi-node layouts. Verify the exact version matrix before committing; the mode names are stable, the LLM CRD is alpha.

"If we do not pick Knative, do we get EPP for free?"

Yes, for routing.  A RawDeployment inference workload is:  Deployment → Pods (+ optional auth sidecar) + Service + HPA
That is exactly the shape LWS has today, minus the leader/worker split. So:
  workload.selector  = the Deployment's Pod labels          ✓ same as LWS
  workload.port      = model port, or 4180 if protected       ✓ same rule as LWS
  routing / epp      = unchanged                              ✓
  Before / After     = the LWS pictures with "leader" replaced by "replica"

No, for the things Knative gave you:
  scale to zero + request buffering   ✗ unless KEDA HTTP add-on (interceptor) or minReplicas ≥ 1
  concurrency-based autoscaling       ✗ HPA/KEDA on other signals
  revision traffic split, tags        ✗ model-name rewrites are the only split left

So the real question is not "Knative or EPP". It is "do these workloads need scale-to-zero and revision rollout badly enough to pay for A or B".

Recommendation (point of view)

Workload profilePick
Always-on LLM serving, GPU pinned, latency mattersC: KServe RawDeployment (or a plain Run:ai Deployment-based inference type). EPP today, no Knative, same code path as LWS.
Bursty, many small models, idle most of the dayKeep Knative without EPP for now; propose B upstream. Scale-to-zero is worth more than smart Pod picking here.
Need both todayA as a time-boxed spike, single revision, feature-flagged.
Prefill/decode, multi-node LLM at scaleWatch D. Do not build on it until it leaves alpha; decide then whether our CRD wraps it or steps aside.
🔧 If you only do one thing: split the Inference workload type by autoscaling need. Knative-backed for scale-to-zero, Deployment-backed (KServe Raw or native) for EPP. One type, two stacks, chosen by a field the user already fills: spec.autoscaling.minReplicas = 0 or not.
01 · Architecture and request flows · before / after (Option A)

Before: Knative picks the Pod and wakes it. After: EPP picks when warm; the Gateway fails over to the Activator when cold.

Before · Knative serving as Run:ai composes it today

Knative already has a smart front door: it buffers at zero, scales on concurrency, and splits traffic by revision. The only blind spot is the final Pod pick, which is random.

🆕 NEW rendered by the InferenceEndpoint controller today · 🔜 PLANNED proposed, not built · green request path · orange cold / fallback path · blue dotted internal · dashed grey = config / metrics
1. Client sends the request to the Knative URL; the Knative ingress terminates TLS and finds the Route.
2. Ask: does the revision have ready Pods?
   → no:  Activator buffers the request and asks KPA for capacity.          ✓ scale from zero
   → yes: the revision Service picks a Pod at random.                        ⚠ no KV / prefix awareness
3. Request enters queue-proxy :8012 → oauth2-proxy (if protected) → model.  ✓ accounting + auth
4. queue-proxy reports concurrency; KPA scales 0 → N → 0.
5. Response streams back the same way.                                       ✓

After · Option A, same workload, Gateway + EPP in front

EPP picks the Pod on the warm path through queue-proxy. When the pool has zero endpoints the Gateway itself fails over to a second backendRef, the Activator Service, so Knative's cold path is reused, not rebuilt, and EPP stays the upstream image.

🆕 NEW rendered by the InferenceEndpoint controller today · 🔜 PLANNED proposed, not built · green request path · orange cold / fallback path · blue dotted internal · dashed grey = config / metrics
1. Client sends the request to the hostname in routing.hostnames; the Gateway terminates TLS.
2. Gateway asks EPP over gRPC; the route already carries the Knative namespace / revision headers.
3. Ask: does the InferencePool have any endpoint?
   → yes: Gateway asks EPP; EPP scores queue · KV · prefix and returns Pod IP:8012.   ✓ smart pick, still via queue-proxy
   → no:  Gateway skips EPP and fails over to the Activator Service backendRef :8012. ✓ Knative wakes the revision as today
4. Gateway forwards the request to that address.
5. queue-proxy → oauth2-proxy (if protected) → model; KPA accounting unchanged.  ✓
6. Response streams back through the Gateway. EPP is not in the stream.        ✓
Never: the model container port, or a Pod of another revision.                 ✗

Detailed sequence · warm path

EPP picks the Pod but the request still enters through queue-proxy, so KPA accounting and the auth sidecar are untouched.

0. EPP scrapes model metrics on each revision Pod's metrics port (not 8012).
1. Client sends the request to the Gateway hostname.
2. Gateway asks EPP; the route already added the two Knative routing headers.
3. EPP sees ready Pods, scores them, picks one.
4. EPP answers with Pod IP:8012.
5. Gateway forwards to queue-proxy.                                 ✓ Knative accounting preserved
6. queue-proxy → oauth2-proxy (if protected) → model.               ✓ auth preserved
7. queue-proxy reports concurrency to KPA as always.
8. Tokens stream back through queue-proxy and the Gateway.
9. Client gets 200 and the stream.                                  ✓

Detailed sequence · cold path (revision at zero)

The only new thing is step 3: the Gateway sees an empty pool and uses the fallback backendRef instead of asking EPP. From step 4 on, this is Knative's own cold start.

🆕 NEW rendered by the InferenceEndpoint controller today · 🔜 PLANNED proposed, not built · green request path · orange cold / fallback path · blue dotted internal · dashed grey = config / metrics
1. Client sends the request.
2. Gateway asks EPP.
3. Gateway sees the InferencePool has zero endpoints → uses the fallback backendRef.   ✓ the trick, EPP not involved
4. (EPP is not consulted on the cold path.)
5. Gateway forwards to the Activator; the Knative-Serving-Revision header tells it which revision.
6. Activator asks KPA for capacity and holds the request.
7. KPA scales the revision 0 → 1; the Pod starts and loads the model.
8. Activator forwards the held request to the new Pod's queue-proxy.
9. Response streams back via Activator and the Gateway.
10. Client gets 200. Next request takes the warm path.              ✓

🧠 Knative is the doorman, EPP is the maître d'. Option A seats people only when the room is open and hands you back to the doorman when it isn't.
